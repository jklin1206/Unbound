Read this first

The fastest way to understand UNBOUND is not by opening random views

Start from the product loop and the completion pipeline. Most screens are just ways to collect input for that pipeline or display the results it writes.

1. Learn the nouns

Rank, LVL, streak, attributes, recovery, movement AP, skill proof, program block, squad mission.

2. Learn the write path

TrainingCompletionService.complete() is the canonical event cascade for finished training.

3. Then read screens

Home, Program, Skills, Squad, and Profile are better understood after the domain services are clear.

Junior engineer trap: treating SwiftUI views as the source of truth. In this app, views should render snapshots and send typed commands. The business rules belong in models, services, catalogs, and stores.
Mental model

The app is a training game loop

UNBOUND takes goals and body inputs, generates training, records proof, awards progression, adapts the next plan, and optionally turns the work into squad progress.

Collect intentOnboarding, profile, equipment, goals, scan checkpoints.
PrescribeProgram generation chooses blocks, days, sessions, and alternatives.
TrainActive workout, routine player, quick log, cardio log, recovery completion.
ProveLogs feed movement AP, rank proof, skills, attributes, streak, rewards.
AdaptProgression engines and recovery context tune tomorrow's work.
SocializeSquad missions, friend challenges, honors, activity, presence.
If a change does not fit into this loop, ask whether it is a product feature, a debug tool, or leftover complexity.

App shell

The app starts in UNBOUND/App/UnboundApp.swift

UnboundApp creates the shared service container, pins dark mode, listens for universal links, starts sync triggers, flushes sync on foreground, applies notification preferences, runs rollover checks, and settles expired friend challenges.

WindowGroupInstalls RootView() with .environmentObject(services).
Universal linksHandles /squad/<code> and posts .squadInviteCodeReceived.
Foreground workTracks app opened, flushes sync, applies notifications, evaluates rollover and friend challenges.
Auth routingRootView chooses loading, onboarding, auth, or HomeTabView.
@main
struct UnboundApp: App {
    @UIApplicationDelegateAdaptor(AppDelegate.self) var appDelegate
    @StateObject private var services = ServiceContainer()
    @Environment(\.scenePhase) private var scenePhase

    var body: some Scene {
        WindowGroup {
            RootView()
                .environmentObject(services)
                .preferredColorScheme(.dark)
                .onContinueUserActivity(NSUserActivityTypeBrowsingWeb) { activity in
                    // /squad/<invite-code>
                }
                .task { SyncTriggers.shared.start() }
        }
    }
}
Root routing

RootView is the launch gate

Routing order

  1. Show AppLaunchLoadingView while auth state is loading.
  2. Show OnboardingContainerView until onboardingCompleted is true.
  3. Show AuthContainerView if onboarding is done but user is signed out.
  4. Show HomeTabView().subscriptionGate() when signed in.

Sign-in side effects

  • Identify analytics user.
  • Replay pending onboarding profile onto authenticated user.
  • Login to subscription service.
  • Backfill attributes from old logs.
  • Ensure current trial week.
  • Restore program cache if missing.
  • Migrate skill tier state from historical logs once.
If onboarding, auth, subscription, sync restore, or initial program state feels weird, start in RootView and follow the async tasks from there.

Most important flow

TrainingCompletionService.complete() is the canonical write path

When a real training session is finished, this service writes the source log and fans out to progression, proof, rewards, streak, skins, squads, and idempotency receipts.

Guard duplicate active completionUses in-memory activeCompletionLogIds and waiters for same-process re-entry.
Check persisted completion recordIf training_completion_records already exists, return already-completed result.
Replay partial receiptsIf replay or progression receipts exist, resume instead of double-writing.
Create performanceLogsSource event is persisted before progression work.
Run progressionMovement AP, body region rewards, attributes, bodyweight, program-aware updates.
Compatible workout logAdapter creates old-compatible WorkoutLog shape for systems that still need it.
Proof engineEvaluates skill/rank proof against current tier state and bodyweight.
Squad progressRecords squad mission and friend challenge progress exactly once per performance log id.
Session logs and reward stateSaves sessionLogs, skin unlocks, streak, replay receipt, final completion record.
Write ownership

What completion is allowed to update

Primary persistence

performanceLogs, training_completion_progression_receipts, training_completion_replay_receipts, training_completion_records.

Compatibility logs

TrainingSessionAdapters.workoutLog(from:) bridges new training sessions into older systems that still consume WorkoutLog.

Rank proof

ProofEngine.evaluate() compares completed work against tier criteria and current UserSkillTierState.

Level and streak

SessionXPService.recordSession() owns streak state and effort leveling. This is not skill rank.

Cosmetics

SkinService.evaluateUnlocks() returns newly earned skins after rank progress.

Squads

recordSquadProgress() calls squad mission and friend challenge services with a source id guard.

If a feature wants to respond to a completed workout, resist adding another random save hook. Prefer a typed output from completion or a service called from the canonical completion path.

Ranking

Rank is ability proof, not effort

RankTier is the single ladder. Movement standards use templates, bodyweight-relative thresholds, bodyweight rep ladders, hold ladders, and proof criteria.

Skill rank

Earned from logged proof in UserSkillTierState, evaluated by ProofEngine.

Movement rank

Derived from movement standards and StrengthStandards templates.

Overall rank

Aggregated through RankService and rank trial logic.

Movement library

MovementCatalog and ExerciseCatalog define what can be trained

Catalogs are data-heavy by design. They connect exercises to rank templates, aliases, rollups, body regions, attributes, skill links, and asset references.

Identity and aliases

Resolve user-facing exercise names, variant spellings, and old ids into rank-standard movement ids.

Training metadata

Body regions, equipment, skill links, progression families, and attribute contribution weights.

Visual assets

Program generation

The Program layer answers "what should the user do next?"

Generation and scheduling

  • DeterministicProgramGenerator builds reproducible blocks from goals, profile, equipment, and constraints.
  • ProgramPhaseEngine understands block/phase context.
  • DailyWorkoutResolver chooses the correct workout for a date/day.
  • BlockRolloverService prepares the next block and checkpoint flow.

State and UI

  • ProgramStore persists local/adopted program state.
  • ProgramViewModel shapes program data for the surface.
  • ProgramOverviewView renders program, routines, and ranks tabs.
  • ActiveWorkoutContainerView turns a draft into completion input.
Program code should decide prescription. Completion code should decide what was earned. Keep that boundary clean.
Program screen

ProgramOverviewView was simplified, but the shell is still large

The simplification pass did break out meaningful pieces around the Program surface. The remaining issue is that ProgramOverviewView.swift itself is still the biggest active view at 4422 lines, so it is not fully decomposed into small ownership units yet.

What was broken out

ProgramRankLibraryView, ProgramFocusSwitchSheet, SavedWorkoutsListView, ScheduleSavedWorkoutSheet, active workout components, and reward components now live outside the main file.

What remains inside

Tab coordination, program preview, routines state, saved workout routing, active workout launch, recovery day completion, checkpoint/rollover, and resume draft orchestration.

Review stance

Treat the file as an orchestration shell. Do not add business logic here; put new rules in ProgramViewModel, a Program service, or a small presenter model.

If explaining a Program change requires a paragraph of "this state triggers that sheet unless this overlay is active," the state model probably needs another pass.

Safe edits

How to make changes without turning the app into spaghetti

When adding a screen feature

  1. Find the owning domain service first.
  2. Add a small view model or derived state if needed.
  3. Keep SwiftUI state for presentation only.
  4. Add a focused test for the rule, not just the button.

When adding training logic

  1. Decide whether it is prescription, completion, proof, or social.
  2. Put the rule in that owner.
  3. Make adapters produce canonical inputs.
  4. Protect idempotency if persistence or social progress is involved.
Good review question: "Can I explain this change as one sentence in the product loop?" If not, the design may be mixing responsibilities.

Glossary

Terms you will see constantly

  • AP: movement progress points, not the same as session XP.
  • Block: a generated chunk of a training program.
  • Checkpoint: scan/profile milestone used for program/body context.
  • Criteria: proof requirement for a skill or rank tier.
  • Draft: pre-session training plan object before active workout.
  • Evidence: logged exercise data used by proof and progression.
  • LVL: total training effort level.
  • Node: static skill graph item.
  • Proof: logged performance satisfying a criterion.
  • RankTier: shared ability ladder.
  • Receipt: persisted idempotency/progression result for a completion.
  • Resolver: code that chooses the correct item from context.
  • Squad mission: weekly backend-authoritative group objective.
  • Streak: consistency counter from session recording.
  • UserSkillTierState: real earned skill rank state.
  • WorkoutLog: compatibility log shape still consumed by several systems.

Final mental model

UNBOUND is complex because training proof touches many systems, but the spine is simple

Screens collect intent and render status. Catalogs define trainable reality. Program services prescribe. Completion services award. Proof services rank. Sync and Supabase persist. Squads react to completed work.

Best first question

Which product-loop phase owns this change?

Best second question

Is this a view concern, a service rule, catalog data, or persistence?

Best review question

Can this be tested without rendering the whole app?

If you keep the canonical training completion path clean, most of the codebase stays explainable.
