Design review

The Program is close to being smart. It is not yet regression-aware.

Current Program Focuses route selected skills into the weekly split and feed workouts into a strong logging and reward pipeline. The missing design layer is the decision engine that chooses the right prerequisite, regression, or progression rung before prescribing the session.

What already works Scheduling, workout editing, RPE logging, autosaved active sessions, quick logs, performance persistence, proof evaluation, XP, streaks, and reward sequence output.
What needs design A smart regression resolver that turns "I want the muscle-up" into "today you train strict pull-up volume, transition drills, or a deload because that is your current rung."
Strong logging surface Authored skill plans exist Regressions not selected programmatically Tier state wiring needs audit

Vocabulary cleanup

There are multiple "goal" and "focus" concepts. They should not share labels.

This is a product design issue, not just naming polish. If the user cannot tell what a focus does, the smart training model will feel like magic instead of coaching.

How Program Focuses work today

A Program Focus is a scheduling pin, not a skill-level intelligence system yet.

User taps Add Program Focus. `SkillDetailView` calls `SkillProgressService.toggleProgramFocus(nodeId:)` if the node is trainable and the cap has room.
The service persists the selected skill id. It still writes `activeGoalIds`, while view code reads the alias `programFocusIds`.
It prefetches the authored RPE session. On add, `RPESessionService.prefetch` warms the skill session for the current user.
The scheduler routes it to the right day type. `ProgramScheduler.category(for: node.cluster)` maps clusters to pull, push, legs, core, skills, or conditioning.

Workout injection

Scheduled skills become `TrainingBlock(kind: .skill)` before the workout starts.

This is the exact place where smart regression should plug in. Today it only inserts the main prescription for the selected skill.

Current call path

  • `ProgramOverviewView.programDraft` builds a draft for the selected day.
  • `DailyWorkoutResolver.programDraft` asks `ProgramScheduler.shared.skillIds(forDate:)` for routed focuses.
  • `TrainingSessionAdapters.skillBlock` converts each skill id into a skill block.
  • The block uses `plan.mainSets.prefix(3)`, not `plan.regressions`.

Design implication

If the user selects muscle-up but their actual current need is false-grip rows or strict pull-ups, the daily draft currently has no resolver step that would choose that lower rung.

The fix is not to make the scheduler smarter. The scheduler should route the focus. A separate resolver should decide the training prescription.

Skill plan anatomy

The data already hints at regression-aware training, but the app does not fully consume it.

Regressions

Lower-skill options for users who are below the standard or need a safer step. Used in Skill Detail's "Train this next" suggestions.

plan.regressions

Main sets

The formal prescription. These are what scheduled Program skill blocks and RPE skill sessions primarily use today.

plan.mainSets

Accessories

Supporting work. RPE skill sessions append these as accessory exercises, usually fixed at two sets of eight.

plan.accessories
The regression library exists. The product decision that is missing is: "Which one should this user do today, and why?"

RPE session behavior

The current intelligence is load and rep tuning from the last session.

This is useful autoregulation, but it answers a narrower question than smart regression.

What it can do

  • Fetch the last `SessionLog` for the skill.
  • For weighted work, adjust load by 2.5 percent per RPE point of headroom.
  • For bodyweight work, suggest adding one rep when RPE is low enough.
  • Show "Last..." notes so the user sees continuity.

What it does not decide

  • Whether the user should regress from the target skill.
  • Whether a prerequisite should replace the target skill for now.
  • Whether a failed or ugly set should trigger a hold, deload, or easier variation.
  • Whether equipment constraints require a different rung.

Completion goal

Goal: every completed session should decide the user's next best rung.

When a user finishes a program workout, skill session, or quick log, UNBOUND should review the evidence, choose progress, hold, regress, or deload, save that decision, and explain the next prescription.

Completed session Program workout, skill session, or quick log.
Evidence bundle Reps, load, hold time, RPE, quality flags, source rung.
Agent reviews Progression, safety, and context checks.
Decision Promote, hold, regress, deload, or block.
Persistence Store the decision beside proof, session, and reward output.
Next prescription The next Program draft uses the updated rung.

Agent reviews

Three structured reviews happen after completion.

Here "agent reviews" means deterministic post-session checks. They can be implemented as small services before any AI layer is added.

Progression review

Did the user earn the next rung through clean repeated evidence, or should the app hold the current prescription?

Safety review

Were there pain, assistance, form-break, high-RPE, missed-range, or fatigue signals that should block proof or reduce difficulty?

Context review

Do equipment, schedule, travel, missed sessions, or the user's weekly split change the next prescription?

Example result

Goal: muscle-up. Current rung: strict pull-up volume. Completed: 3x5 clean at RPE 7 with no pain. Review result: promote to chest-to-bar prep next pull day.

Smart regression feasibility

Yes, this is doable programmatically. Add a resolver between scheduler and draft creation.

The scheduler should answer "when do we train this focus?" The resolver should answer "what is the correct version for this user today?"

Aspirational target User selects muscle-up, planche, L-sit, or another goal skill.
Skill graph Read prerequisites, tier criteria, cluster, and unlock state.
Training rungs Combine regressions, prerequisites, main sets, and accessories into ordered options.
User evidence Use logs, RPE, flags, recency, equipment, pain, bodyweight.
Resolver decision Choose rung, prescription, reason, confidence, next promotion test.
Program block Daily draft receives the right exercise now, not just the dream skill.

Decision model

Promotion should be earned by clean repeated evidence, not a single heroic set.

Promote to harder rung when...

  • Target reps or hold time are met for 2 of the last 3 exposures.
  • Average or top-set RPE is at or below the threshold, usually 8.
  • Quality flags are clean and no pain/form-break flags appear.
  • Rest time and range standards match the rung definition.
  • The next rung is compatible with available equipment.

Hold, deload, or regress when...

  • RPE is repeatedly above target or reps fall below the minimum.
  • Quality flags show pain, assistance, uncontrolled reps, or range loss.
  • The user returns after a long break.
  • The target skill is locked by prerequisites.
  • The selected equipment cannot support the current rung safely.
The smart move is not always harder. Sometimes "smart" means hold the rung until it is clean enough to count.

Data model proposal

Add explicit training rungs and persist the resolver's decision.

Right now `TrainingExercise` options are human-readable candidates. A smart coach needs structured rungs with criteria, equipment, and logging identity.

`SkillTrainingRung`

  • `id`, `skillId`, `title`, `levelIndex`
  • `source`: prerequisite, regression, main, accessory, deload
  • `prescriptions`: sets, target, rest, notes
  • `equipmentRequirements` and substitution options
  • `promotionCriteria` and `regressionCriteria`

`SkillProgressionDecision`

  • `targetSkillId` and `selectedRungId`
  • `state`: learning, ready, proving, deload, blocked
  • `reason`: why this exercise today
  • `confidence` and evidence summary
  • `nextCheck`: what would promote or hold the user

UX recommendations

The UI should explain the decision without making the user study the algorithm.

Program tab

  • Show Program Focuses even when none route today, with "next focus day" visibility.
  • Rename whole-program focus switching to Training Mode.
  • For each focus, show "Working on: strict pull-up" under "Goal: muscle-up."
  • Keep the weekly schedule editor as the user's routing control.

Logging surface

  • Show one concise reason: "You hit 3 clean sets at RPE 7 last time."
  • Ask for RPE and quality flags on skill rungs because those drive decisions.
  • When the resolver holds or regresses, name the reason plainly.
  • Let the user override, but mark it as an override in the decision record.

Current risks

The biggest risks are not technical difficulty. They are consistency and trust.

Hidden focuses

`todaysTrainingSection` is only shown when routed focus sessions exist today, so the empty state inside the section may not appear. A user can have focuses and not see them on a non-focus day.

Locked aspiration conflict

`toggleProgramFocus` requires `isNodeTrainable`, but smart progression often starts with a locked aspiration and trains the prerequisite path.

State wiring audit

`RankService.evaluateTierCrossings` and `SkillProgressService.recompute` appear to have limited production call coverage. Smart decisions need a reliable post-completion update hook.

Agent review findings

The reviews agree on the loop: choose the rung before training, update the rung after completion.

Product review tightened the story. Technical review checked the code path and guardrails.

Product review

  • Lead with "the app learns from every completed session."
  • Define reviews as structured checks, not mysterious external reviewers.
  • Keep the user model simple: goal, current rung, review.
  • Separate pre-workout selection from post-workout review.

Technical review

  • Current Program Focuses are scheduling pins, not smart regression goals.
  • The insertion point is before `TrainingSessionAdapters.skillBlock` builds prescriptions.
  • Use the same resolver in Program drafts and standalone RPE skill sessions.
  • Completion must explicitly store rung evidence and wire tier/node persistence.

Shared recommendation

Add `SkillRungResolver` between scheduler and adapters. Feed it authored regressions, main sets, accessories, logs, quality flags, RPE, equipment, and current tier/node state.

Claims to avoid

Do not claim smart regression exists today, locked skills can be Program Focuses today, regression work proves the strict parent skill, or skill-only focus work completes a Program day.

Implementation roadmap

Build the smart layer in thin slices.

Introduce structured rungs. Convert `regressions`, prerequisites, and main sets into ordered `SkillTrainingRung` records without changing UI behavior yet.
Add `SkillProgressionResolver`. Given target skill, user id, date, equipment, logs, and quality history, return a `SkillProgressionDecision`.
Inject decisions into Program and skill sessions. Replace `TrainingSessionAdapters.skillBlock(skillId:title:)` with a decision-aware block builder, and use the same resolver in `RPESessionService`.
Run agent reviews on completion. Attach rung IDs to logs, review evidence, persist the progression decision, and update the next scheduled skill block.
Expose reasons in the UI. Show current rung, why it was selected, and what unlocks the next rung.

Build goal

Keep the user model simple: goal, current rung, review.

The deck and implementation should both teach the same model: goal is where I want to go, current rung is what I train today, review is why it changes.

Definition of done

  • Every skill block has a target skill id and selected rung id.
  • Completion records reps, load, hold time, RPE, flags, and source rung.
  • The next Program draft reflects the latest decision.
  • The UI explains the decision in one short reason.

First-slice non-goals

  • No fully generative AI exercise writing.
  • No demotion of already earned rank proof.
  • No hidden auto-advance without logged evidence.
  • No changing the weekly scheduler's routing job.

Pass condition

The implementation goal is ready when technical and product review agree on the same loop: resolver before workout chooses today's rung; completion after workout updates tomorrow's rung.

Block condition

Do not implement if completion cannot reliably attach actual logged evidence to the selected rung. Without that link, the resolver cannot learn from the user.
